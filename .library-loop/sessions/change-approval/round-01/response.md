Version 0.17.0. A change plan is a proposal: `wiki.change(plan)` and `wiki_change` validate the plan, write the change document with `status: proposed`, and link it from the session; nothing under `wiki/` changes until a person approves. `wiki.approve(path)` reads the plan back from the document, validates it again, snapshots, applies, snapshots, and sets `applied`; `wiki.reject(path, reason)` sets `rejected` with the reason. The reads for a view are `wiki.changes(status?)`, `wiki.changeDetails(path)` (each write with `before`, `after`, and `changed`), and `wiki.changeActs(change)` (approve and reject while proposed, with a label and a `run`). `createYami` adds `Wiki: approve this change`, `Wiki: reject this change`, `Wiki: approve a change`, and `Wiki: reject a change`. `onSessionsChange` hears of each change document, with a test over the fake app. The ingest ends at the proposal: `change-applied` and `sources-absorbed` have the module's checks `proposed` and `absorbed`; `clean-topics` has no check, and the review judges it (R8: a code check over the real wiki is wrong before the approval, since a pending source has no description yet, and a lint over the proposal as if applied would need a second index per check; the review has the change document and `wiki_lint`). A rejected change unmets both checks, and their details name it with the person's reason, so a resume's feedback holds it. The return of a checkout proposes and approves in one step, and its tests did not change. The README's "Changes and versions", the wiki module section, the commands table, and the prompts table document it all; the CHANGELOG lists the break of `change()` and how to migrate. `npm run build` and `npm test` pass (495 tests).

## Policy
Add to "The wiki", item 8: "The change document is the one record of the plan. An approval reads the writes back from it, so a hand edit that keeps the document's form is applied as written, and one that breaks the form is refused with a message that says so."
